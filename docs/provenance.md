# Release provenance & verification

Every published KhulnaSoft Action release is traceable from source commit to
registry digest. This document describes the threat model, what is proven,
and how to verify a release independently of the publishing workflow.

## Threat model

We assume the publishing pipeline (`publish-release.yml`) can be subverted —
compromised credentials, a malicious dependency in the build, or a tampered
registry entry. The goal is that a consumer can detect a bad artifact even if
the workflow itself lies.

| Threat | Mitigation |
| ------ | ---------- |
| Tag moved to different commit | `verify_release.py` resolves the tag via `git ls-remote` and compares to the recorded commit |
| Version files inconsistent with tag | `version.txt` is re-fetched at the tagged commit and compared |
| Registry image swapped after push | Both registries must resolve to the same manifest digest; the release manifest records the digest at publish time |
| Build not run from claimed source | SLSA provenance (`provenance: mode=max`) + signed GitHub artifact attestations bind the image digest to the workflow run and commit |
| SBOM detached from image | SBOM is generated from the digest-pinned image (`image@sha256:...`) and itself attested |
| Release notes/assets tampered | Manifest + SBOM are attached as release assets only after the verify job passes |

## What a release produces

For each release of an action (`<action>/vX.Y.Z`):

1. **Git tag** `<action>/vX.Y.Z` on the release-prep commit (version bump).
2. **Two registry images** with identical manifest digests:
   - `khulnasoft/actions-<action>:<version>` (Docker Hub)
   - `ghcr.io/khulnasoft/actions/<action>:<version>` (GHCR)
3. **BuildKit provenance + SBOM** as OCI referrers on each image
   (`provenance: mode=max`, `sbom: true` on `build-push-action`).
4. **Signed attestations** (`actions/attest-build-provenance`, Sigstore /
   GitHub artifact attestations) for:
   - the GHCR image digest (`push-to-registry: true`)
   - the Docker Hub image digest (`push-to-registry: true`)
   - the SPDX SBOM file
5. **`release-manifest-<action>.json`** — schema
   `khulnasoft/release-manifest/v1` recording action, version, tag, commit,
   per-registry image digests, SBOM SHA-256, and the workflow run URL.
6. **`sbom-<action>.spdx.json`** — SPDX JSON SBOM generated by syft from the
   digest-pinned GHCR image.

Assets 5–6 are attached to the GitHub Release by the `release-assets` job,
which runs only after the `verify` job passes.

## Verifying a release independently

`verify_release.py` performs all checks below without trusting the
publishing workflow. It needs `git`, `docker buildx`, network access to
GitHub and both registries, and (for `--attest`) `gh` with `GH_TOKEN`.

```bash
python scripts/verify_release.py \
  --action issue-manager \
  --version 0.6.1 \
  --manifest release-manifest-issue-manager.json \
  --attest
```

Checks performed:

- `git ls-remote` resolves `<action>/vX.Y.Z` to a commit (`--expect-commit`
  asserts it).
- `<action>/version.txt` at that commit equals `X.Y.Z`.
- `docker buildx imagetools inspect` resolves both registry tags; digests
  must agree across registries and with the manifest when supplied.
- `gh attestation verify oci://<image>@<digest>` for both images.

To verify the SBOM attestation manually:

```bash
gh attestation verify sbom-issue-manager.spdx.json --owner khulnasoft
```

## Reproducibility status

Builds are **not currently bit-for-bit reproducible**. Addressed so far:

- The base image is pinned by digest (`python:3.14-slim@sha256:…`) in every
  `base.dockerfile`, so the base no longer floats.
- Direct runtime dependencies in each `requirements.txt` are pinned to exact
  versions.

Remaining sources of nondeterminism:

- Transitive dependencies are still resolved by `pip` at build time (direct
  pins do not constrain them). Full reproducibility requires a compiled lock
  file with hashes.
- Image config timestamps differ per build.

The `repro-check` job in `container-build.yml` (manual dispatch, `ref`
input) builds each action twice without cache and compares RootFS layer
`diff_ids`, reporting identical/differing layers in the job summary. This
detects content drift; registry digest equality across rebuilds is *not*
expected today.

If bit-for-bit reproducibility becomes a requirement, the remaining path is:
compile a fully pinned lock file (`pip-compile`/`uv pip compile` with hashes)
and set `SOURCE_DATE_EPOCH` with BuildKit's `rewrite-timestamp`.
